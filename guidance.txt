### 3. 再读分块

阅读：

[chunker.py](file:///g:/code/school-rag-master/indexer/chunker.py#L69-L217)

分块是 RAG 中非常容易被面试官追问的部分。

当前项目大致使用：

```text
chunk_size = 1024
chunk_overlap = 120
doc_keep_size = 2048
```

为什么需要分块？

- 文档太长，无法全部放入 Prompt。
- 整篇文档向量过于粗糙，检索不准确。
- 小片段更容易与用户问题匹配。

为什么需要 overlap？

假设一句话刚好被切在两个 chunk 之间，没有重叠的话，上下文可能被破坏。重叠可以保留边界信息，但过大会导致：

- chunk 数量增加
- 索引体积增大
- 检索结果重复
- Prompt 成本提高

面试回答可以采用这个结构：

> 我先用固定大小分块作为基线，再根据召回率和上下文完整性调节 chunk size 和 overlap。学校通知通常有标题、时间、对象、办理流程等结构，因此后续可以进一步按段落或标题感知分块，而不是完全依赖字符长度。

### 4. 再读 Embedding

阅读：

[embedder.py](file:///g:/code/school-rag-master/indexer/embedder.py#L22-L165)

Embedding 的作用是：

```text
文本
  -> 一个固定维度的向量
```

例如：

```text

  -> [0.12, -0.03, ..., 0.87]
```

语义相近的文本，向量距离通常也更近。

项目默认使用：

```text

维度：1024
距离：cosine
```

需要重点理解一个面试问题：

> 为什么查询和文档都要使用同一个 Embedding 模型？

因为它们必须位于同一个向量空间中。否则查询向量和文档向量的距离没有可比性。

还要注意 BGE 查询前缀：

```text
为这个句子生成表示以用于检索相关文章：
```

你可以实际做一个实验：


```text

是否相关
最相关结果的排名
```

这会成为你后续讲“检索效果”的真实材料。

阅读：

- [vector_store.py](file:///g:/code/school-rag-master/indexer/vector_store.py#L32-L170)

## 五、第四步：理解检索质量，而不只是“能搜索”

当前项目的检索器不是单纯向量搜索，还包含：

```text
向量检索
  + BM25 关键词检索
  -> RRF 融合
  -> Reranker 重排
  -> 文档去重
```

对应：

- [retriever.py](file:///g:/code/school-rag-master/rag/retriever.py#L264-L558)
- [bm25_search.py](file:///g:/code/school-rag-master/indexer/bm25_search.py)
- [reranker.py](file:///g:/code/school-rag-master/indexer/reranker.py#L67-L134)

### 为什么需要混合检索？

向量检索擅长：

```text
语义相似
同义表达
自然语言问题
```

BM25 擅长：

```text
精确关键词
通知编号
文件名称
专业名词
时间和数字
```

例如：

```text
查询：2025 年校内文件 123 号
```

BM25 可能比纯向量检索更可靠。

### 为什么还要 Reranker？

第一阶段召回可以多拿一些候选，例如 Top 20。然后使用 Cross-Encoder 对：

```text
(query, document_chunk)
```

进行更精细的相关性判断，最后保留 Top 5。

可以把它总结成两阶段检索：

```text
Recall：
  快速、大范围召回候选

Rerank：
  慢速、精确排序
```

### 你应该做的对比实验

准备 20 个真实问题，分别测试：

```text
只用向量检索
向量 + BM25
向量 + BM25 + Reranker
```

记录：

```text
Top 1 是否相关
Top 3 是否包含正确资料
Top 5 是否包含正确资料
检索耗时
```

面试时不要只说“用了混合检索”，而要说：

> 我做了消融对比，发现纯向量检索对语义问题较好，但对通知编号、日期和专有名词不稳定，所以加入 BM25；之后再用 Reranker 提升候选结果的精确排序。

## 六、第五步：理解 RAG 生成阶段

生成阶段的本质是：

```text
用户问题 + 检索到的上下文
  -> Prompt
  -> LLM
```

项目会将检索结果组织成类似内容：

```text
文档 1
来源站点：教务部
标题：选课通知
来源 URL：...
正文片段：...

文档 2
来源站点：...
标题：...
正文片段：...
```

然后交给模型。

需要重点理解三个风险。

### 1. 幻觉

如果检索结果不相关，模型可能仍然强行回答。

因此 Prompt 应明确要求：

```text
只根据提供的资料回答
资料不足时明确说明
不要编造官网没有的信息
给出来源
```

### 2. 上下文过长

检索结果太多会导致：

- 超出上下文窗口
- 重要信息被稀释
- 成本增加
- 延迟变高

项目对每个检索结果限制了上下文长度，相关逻辑在：

[generator.py](file:///g:/code/school-rag-master/rag/generator.py#L172-L195)

### 3. 来源溯源

回答不能只有一段文字，还要能说明：

```text
答案来自哪个文档
原始 URL 是什么
对应的正文片段是什么
```

这也是学校官网问答系统相比普通聊天机器人的重要价值。


面试官可能问：

> 为什么需要流式接口？

> 大模型生成具有明显延迟。如果等待完整答案生成后一次性返回，用户会感觉系统没有响应。SSE 可以先返回检索结果和来源，再持续返回生成 token，改善首字节响应时间和交互体验。

还要理解当前实现中的一个问题：

- `/api/health` 主要检查 Chroma 和 SQLite。
- 它不一定能发现 Embedding 模型、BM25 或 LLM 不可用。
- 流式接口在没有检索结果时，可能直接结束而不返回固定的无结果文本。

这些都是你可以在重构时修复，并在面试中作为工程思考来讲的点。

### 1. 一分钟项目介绍

可以按照这个模板组织：

> 这是一个面向学校官网的 RAG 智能检索系统。离线阶段通过爬虫获取网页和 PDF，经过解析和文本分块后，使用 BGE 模型生成向量并存入 Chroma，同时将文档元数据写入 SQLite。在线阶段先对用户问题进行向量检索，也可以结合 BM25 和 Reranker 提升召回质量，再将相关片段、来源和用户问题组织成 Prompt，调用 DeepSeek 生成带来源的回答。后端使用 FastAPI，前端使用 Vue3，并通过 SSE 实现流式输出。

不要直接背这段。你需要能根据代码解释每个名词。

### 2. 系统架构图

你应该自己画出：

```text
Crawler
  -> Raw Files
  -> ParserRouter
  -> ParsedDocument
  -> TextChunker
  -> Embedder
  -> Chroma / SQLite

Query
  -> Retriever
  -> Vector Search / BM25
  -> RRF
  -> Reranker
  -> Generator
  -> DeepSeek
  -> Answer + Sources
```

### 3. 关键参数表

至少记录：

```text
chunk_size
chunk_overlap
top_k
embedding model
embedding dimension
similarity metric
BM25 参数
RRF k
reranker model

```

同时记录每个参数改变后对结果的影响。

### 4. 问题和解决方案

准备真实案例：

```text
网页正文提取不干净，怎么办？
PDF 是扫描件，怎么办？
检索不到正确通知，怎么办？
答案出现幻觉，怎么办？
同一篇文档重复出现，怎么办？
上下文太长，怎么办？
LLM 调用失败，怎么办？
首次请求为什么很慢？
如何支持流式输出？
如何评估 RAG 效果？
```

每个问题都按下面格式回答：

```text
现象
原因
解决方案
代价或副作用
如何验证
```

## 十、建议你马上做的第一轮任务

按这个顺序执行：

1. 阅读 [parser/base.py](file:///g:/code/school-rag-master/parser/base.py#L19-L70)，理解 `ParsedDocument`。
2. 阅读 [indexer/chunker.py](file:///g:/code/school-rag-master/indexer/chunker.py#L69-L217)，手动拿一篇文本测试分块。
3. 阅读 [indexer/embedder.py](file:///g:/code/school-rag-master/indexer/embedder.py#L22-L88)，理解文本到向量的过程。
4. 阅读 [indexer/vector_store.py](file:///g:/code/school-rag-master/indexer/vector_store.py#L32-L170)，理解写入和查询。
5. 阅读 [rag/retriever.py](file:///g:/code/school-rag-master/rag/retriever.py#L264-L558)，先只关注纯向量检索部分。
6. 阅读 [rag/generator.py](file:///g:/code/school-rag-master/rag/generator.py#L80-L195)，理解 Prompt 和 LLM 调用。
7. 用一个问题手动调用 `RAGChain.search_only()`。
8. 再调用 `RAGChain.ask()`，比较纯检索结果和带 LLM 的答案。
9. 最后阅读 API 和前端。

你当前最重要的目标不是“把整个项目背下来”，而是做到：

> 给定一个用户问题，你能从 API 入口一路追踪到检索、Prompt、LLM 和最终响应；给定一篇官网文章，你能解释它如何变成向量并被检索出来。

做到这两点后，再加入爬虫、混合检索、Reranker 和前端，面试时就能从原理、代码和工程取舍三个层面回答。
